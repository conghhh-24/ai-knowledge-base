# 2. @RestController 原理

## 我的理解

`@RestController` 表示：

> 这个类负责处理 HTTP 请求，并直接返回数据给客户端。

它等价于：

``` java
@Controller
@ResponseBody
```

------------------------------------------------------------------------

## 请求流程

    浏览器
     |
     | GET /health
     ↓
    Tomcat服务器
     |
     ↓
    Spring MVC DispatcherServlet
     |
     ↓
    找到 HealthController
     |
     ↓
    执行 health()
     |
     ↓
    返回响应数据

------------------------------------------------------------------------

## 为什么需要它？

如果没有：

``` java
@RestController
```

Spring 不知道这个类是接口控制器。

访问：

    /health

可能返回：

    404 Not Found

------------------------------------------------------------------------

## 面试表达

> @RestController 是 Spring MVC 提供的组合注解，用于声明 REST
> 风格控制器，相当于 @Controller 加 @ResponseBody，使方法返回值直接作为
> HTTP 响应数据返回。

# 3. Docker 端口映射

配置：

``` yaml
ports:
  - "3307:3306"
```

含义：

    宿主机端口 : 容器端口

实际：

    IDEA(Spring Boot)
            |
            |
     localhost:3307
            |
            |
     Docker
            |
            |
     MySQL容器:3306

------------------------------------------------------------------------

## 我的理解

3307：

-   是电脑访问 Docker 的入口

3306：

-   是 MySQL 在容器内部监听的端口

------------------------------------------------------------------------

## 为什么不用直接暴露3306？

因为电脑已经安装 MySQL，占用了3306这个端口。

所以：

    电脑3307
    映射
    容器3306

避免冲突。

------------------------------------------------------------------------

# 4. localhost 的理解

## 当前开发环境

Spring Boot 在 IDEA 中运行：

    IDEA
     |
     |
    localhost

所以：

    jdbc:mysql://localhost:3307

表示：

连接我自己电脑的3307端口。

------------------------------------------------------------------------

## Docker环境中的区别

以后：

    backend容器
     |
     |
    mysql容器

不能使用：

    localhost

因为：

容器里的 localhost 指向自己。

应该使用：

    mysql:3306

其中：

mysql 是 docker-compose 中的服务名。

# 8. 数据库设计学习

## 第一层：先知道"它解决什么问题"

数据库表的作用：

> 解决应用程序中数据如何长期保存、查询和管理的问题。

如果没有数据库：

-   用户注册信息无法保存
-   上传的文档关闭程序后会丢失
-   AI问答记录无法查看历史

所以数据库负责：

    程序
     |
     | 保存/读取数据
     ↓
    MySQL数据库

在 AI 知识库项目中，需要保存：

-   用户信息
-   用户上传的文档
-   用户和 AI 的聊天记录

因此设计了三张核心表：

    user
     |
    document
     |
    chat_message

------------------------------------------------------------------------

## 第二层：理解项目里的位置

当前项目：

    ai_knowledge_base

    MySQL
     |
     +-- user
     |
     +-- document
     |
     +-- chat_message

### 1. user 用户表

解决：

> 谁在使用系统？

保存：

    id
    username
    password_hash
    status
    create_time
    update_time

关系：

一个用户可以上传多个文档。

    user 1 ---- N document

------------------------------------------------------------------------

### 2. document 文档表

解决：

> 用户上传的知识资料如何保存？

保存：

    id
    user_id
    file_name
    file_path
    file_type
    file_size
    status
    create_time
    update_time

其中：

    user_id

表示：

这个文件属于哪个用户。

------------------------------------------------------------------------

### 3. chat_message 聊天记录表

解决：

> 用户和 AI 的问答历史如何保存？

保存：

    id
    user_id
    document_id
    question
    answer
    create_time

例如：

用户：

    请总结这个PDF

AI：

    这是文档总结...

都会保存到这里。

------------------------------------------------------------------------

## 第三层：最后补原理

### 1. 主键 Primary Key

每张表都有：

    id

作用：

唯一标识一条数据。

例如：

    user

    id username

    1  张三
    2  李四

id不能重复。

------------------------------------------------------------------------

### 2. 外键 Foreign Key

表之间通过外键关联。

例如：

document：

    user_id

关联：

    user.id

表示：

    这个文档属于哪个用户

关系：

    user.id
            |
            |
    document.user_id

------------------------------------------------------------------------

### 3. 一对多关系

项目中：

    一个用户
        |
        |
    多个文档

叫：

    1 : N

原因：

一个用户可以上传很多资料。

------------------------------------------------------------------------

### 4. 为什么需要数据库关系设计？

如果所有数据放一张表：

    用户+文件+聊天

会导致：

-   数据重复
-   修改困难
-   查询效率低

拆成多张表：

    user

    document

    chat_message

符合数据库设计原则：

-   减少重复
-   方便维护
-   方便扩展
